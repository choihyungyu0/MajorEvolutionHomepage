검토 PR: #11 `Build guided professor and research journeys`

## 오늘의 한 문장

기능을 더 늘리기보다, 학생이 `내 고민 정리 → 현실적으로 접근 가능한 첫 교수 선택 → 첫 대화 준비`와 `AI 프로젝트 설계 → 프로젝트에 맞는 교수 추천`이라는 두 여정을 헤매지 않고 끝낼 수 있도록 구조를 다시 정리했습니다.

## 1. 오늘 해결한 문제와 제품 판단

### 문제 A — 홈과 서비스 첫 화면에 정보가 너무 많았음

- 수정 전: 기능·설명·카드가 한 화면에 함께 쌓여 사용자가 다음 행동을 다시 해석해야 했습니다.
- 판단: 첫 화면은 모든 기능을 설명하는 곳이 아니라 현재 상태에서 할 일 하나를 알려주는 곳이어야 합니다.
- 수정: 홈, 교수 매칭, 교수 만남 연계, 성장 기록을 `허브 → 오늘의 한 과업 → 전용 상세` 구조로 분리했습니다.

### 문제 B — 아이디어 기능만 다시 긴 입력 폼으로 시작했음

- 수정 전: 교수 매칭 튜토리얼은 한 질문씩 진행하지만 프로젝트 아이디어는 긴 폼이 먼저 나왔습니다.
- 판단: 선택적 심화 기능도 같은 학습 규칙을 가져야 합니다.
- 수정: 전공 → 탐색 방식 → 관심 → 경험·방법 → 기간·자료 → 확인의 6단계 튜토리얼로 만들고, 마지막 확인 전에는 기존 교수 연결 상태를 바꾸지 않게 했습니다.

### 문제 C — AI 공동설계 질문이 사실상 고정형이었음

- 수정 전: 사용자마다 답이 달라도 같은 질문 흐름을 받았습니다.
- 판단: 비교 가능한 최소 공통 질문과 실제 개인화를 분리해야 합니다.
- 수정: 공통 질문 3개 뒤 OpenAI API가 앞선 답변에 맞는 후속 질문 2개를 생성합니다. 실패하면 검수된 기본 질문으로 이어져 흐름이 끊기지 않습니다.

### 문제 D — 학생 고민용 교수 연결과 프로젝트 멘토 연결이 섞였음

- 수정 전: 두 결과 모두 비슷한 3인 추천처럼 보여 성공 기준이 모호했습니다.
- 판단: 첫 연결은 학생의 전공·진로 고민, 두 번째 연결은 선택 프로젝트의 성공에 필요한 주제·방법·응용 전문성으로 구분해야 합니다.
- 수정: 프로젝트 추천에서는 공식 데이터 규칙으로 후보를 먼저 좁힌 뒤 AI가 주제·방법·확장 역할을 재정렬하도록 분리했습니다. AI는 후보 밖 교수나 면담 가능성을 만들 수 없습니다.

### 문제 E — 3인 교수 피칭에서 다음 행동이 복잡했음

- 수정 전: 세 카드의 정보와 여러 버튼이 한꺼번에 보여 어떤 교수를 왜 먼저 선택할지, 선택 뒤 어디로 가는지 판단해야 했습니다.
- 판단: 본인 학과 교수는 전공 맥락을 설명하고 접근하기 상대적으로 쉬운 현실적인 첫 접점입니다. 동시에 다른 학과 전문성을 선택지로 열어둬야 합니다.
- 수정:
  1. 같은 학과 교수 1명 — `같은 학과 연결 · 가까운 시작점`
  2. 다른 학과 교수 1명 — `주제 연결형`
  3. 다른 학과 교수 1명 — `방법 연결형`
- 세 후보는 순위가 아닙니다. 같은 학과 소속과 연구주제 적합성도 별도 근거로 설명합니다.
- 카드의 주 행동은 `이 교수님과 첫 대화 준비하기` 하나로 줄이고, 누르면 `/quest`로 바로 이동합니다. 출처·논문·다른 후보 찾기는 `더 보기` 안에 두었습니다.
- 모바일은 세 카드를 길게 세로로 쌓지 않고 한 장씩 좌우로 넘겨 비교하도록 바꿨습니다. PC는 세 장을 동시에 비교합니다.

## 2. 내비게이션을 두 여정으로 정리

`홈 → 교수 매칭 → 교수 만남 연계 → AI 프로젝트 설계 → 맞춤 교수 추천`

- 교수 여정: 학생의 고민 정리 → 교수 매칭 → 첫 대화·이메일·면담 준비
- 프로젝트 여정: AI와 프로젝트 설계 → 후보 선택 → 프로젝트에 맞는 교수 추천
- `맞춤 교수 추천`은 진행 상태에 따라 프로젝트 시작, 후보 선택, 추천 근거 중 필요한 다음 행동만 보여줍니다.

## 3. 디자인 원칙 수정

- 8px 간격 체계와 8/12/16px 반경으로 통일
- 보라 그라데이션·강한 그림자·발광 장식을 줄이고 단색 CTA 사용
- 비슷한 카드를 반복하기보다 열린 행과 접힌 상세 사용
- 모바일에서는 한 화면의 판단량과 스크롤을 줄이고, 48px 이상의 터치 영역 유지
- 생성형 장식보다 실제 학생의 상태·근거·다음 행동이 먼저 보이게 수정

## 4. 멘토링 때 보여드릴 4분 시연

1. `/home` — 저장 상태에 따라 다음 행동 하나가 달라지는 모습
2. `/tutorial` → `/professors/pitch` — 고민을 정리하고 같은 학과 1명·타 학과 2명을 받는 과정
3. 교수 카드의 `첫 대화 준비하기` → `/quest` — 선택 한 번으로 행동 단계에 진입
4. `/co-design` → `/result` → `/project-professors` — 공통 3문항·맞춤 2문항과 프로젝트 전용 교수 추천

## 5. 오늘 멘토님께 확인받을 질문

1. 첫 교수 후보를 `같은 학과의 가까운 시작점`으로 고정하는 원칙이 대학생의 실제 접근 장벽을 낮추는 데 설득력 있는가?
2. 나머지 두 후보를 `주제 연결형·방법 연결형`으로 구분하면 서로 다른 선택 이유가 충분히 전달되는가?
3. 같은 학과 소속과 연구 적합성을 별도로 설명하는 현재 신뢰 문구가 오해를 막기에 충분한가?
4. 교수 선택 직후 홈을 거치지 않고 대화 준비로 바로 보내는 흐름이 자연스러운가?
5. 프로젝트 교수 추천에서 `공식 후보 제한 → AI 역할 재정렬`의 책임 경계가 서비스 장점으로 이해되는가?
6. 최종 발표에서는 기능 수보다 `추천 앱 → 실제 첫 대화와 다음 행동을 만드는 서비스`로 바뀐 성장 과정을 중심에 두는 것이 적절한가?
