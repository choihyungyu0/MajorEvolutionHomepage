# [UNIKER 1기 / 팀 트리온] 추천 앱에서 첫 대화를 만드는 서비스로 — ‘너의 교수님은?’ 최종 개발 기록

안녕하세요. 커널아카데미 UNIKER 1기 AI 크루로 활동하고 있는 팀 트리온입니다. 팀장 이연수, 팀원 최현규·이진재가 함께 대학생의 전공·진로 고민을 교수와의 실제 대화로 연결하는 AI 서비스 ‘너의 교수님은?’을 만들고 있습니다.

이번 주 목표는 기능을 더 많이 보여주는 것이 아니었습니다. 처음 방문한 학생이 서비스 안에서 길을 잃지 않고, 자신의 고민을 정리한 뒤 교수에게 첫 질문을 건넬 준비까지 끝낼 수 있도록 전체 흐름을 다시 설계하는 것이었습니다.

## 처음에는 ‘잘 맞는 교수’를 추천하려고 했습니다

처음 기획한 서비스는 AI가 학생의 전공과 관심사를 분석해 연구 아이디어와 잘 맞는 교수를 추천하는 앱이었습니다. 전공 DNA, 교수 궁합 점수, 추천 순위를 활용하면 결과를 빠르게 이해할 수 있을 것이라고 생각했습니다.

하지만 화면을 실제로 만들고 멘토링을 받을수록 두 가지 문제가 분명해졌습니다.

첫째, 학생이 그 점수와 순위를 왜 믿어야 하는지 설명하기 어려웠습니다. 공개된 교수 정보만으로 교수와 학생의 궁합이나 프로젝트 성공 가능성을 숫자로 단정하는 것은 오해를 만들 수 있었습니다.

둘째, 추천 결과를 확인한 다음 행동이 없었습니다. 교수 카드가 아무리 풍부해도 학생이 “이 교수님께 어떤 말로 연락해야 하지?”에서 다시 막히면 서비스가 해결한 문제는 절반에 불과했습니다.

그래서 제품의 중심 질문을 바꿨습니다.

> “어떤 교수를 추천할까?”가 아니라, “학생이 믿을 수 있는 근거를 확인하고 실제 교수와 첫 대화를 시작하려면 무엇이 필요할까?”

[사진 2. `10-evolution-before-after.png` — 초기 추천 중심 화면과 현재 행동 중심 서비스 비교]

이 질문을 기준으로 교수 궁합 점수와 순위를 제거했습니다. 대신 학교·학과·교수 공식 프로필, 학생과 교수의 관심이 만나는 연결 이유, 교수에게 직접 확인해야 할 질문을 구분해 보여주었습니다. AI가 결정을 대신하는 것이 아니라 학생이 판단할 수 있도록 재료를 정리하는 방향으로 역할을 바꾼 것입니다.

## 이번 주에 해결하려고 했던 문제

기능을 하나씩 연결하면서 또 다른 문제가 생겼습니다. 홈, 교수 매칭, 만남 준비, 프로젝트 설계, 성장 기록이 한 서비스 안에 들어오자 한 화면에 설명과 카드가 너무 많이 쌓였습니다. 사용자는 서비스를 이용하기 전에 긴 화면을 내려보며 다음 버튼을 다시 찾아야 했습니다.

이번 주에는 토스의 모바일 디자인 원칙처럼 사용자가 불필요한 판단을 반복하지 않도록 다음 세 가지 기준을 세웠습니다.

- 한 화면에서는 하나의 핵심 행동을 먼저 보여준다.
- 사용자의 현재 진행 상태에 맞는 다음 행동을 제안한다.
- 자세한 도구와 설정은 필요할 때 들어가는 별도 화면으로 분리한다.

새 기능을 늘리기보다 사용자가 기능 사이에서 길을 잃게 만드는 지점을 줄이는 데 집중했습니다.

[사진 3. `before-after-2026-08-24/01-home-before-after.png` — 기능 나열형 홈에서 현재 상태 기반 홈으로 바꾼 전후 비교]

## 교수 연결과 프로젝트 설계를 두 개의 여정으로 나눴습니다

기존에는 교수 추천과 프로젝트 아이디어 기능이 비슷한 결과 화면으로 보였습니다. 하지만 두 기능에서 교수를 찾는 이유는 다릅니다.

첫 번째 여정은 학생 개인의 전공·진로 고민을 위한 연결입니다.

`3분 고민 정리 → 첫 교수 매칭 → 첫 대화 준비 → 면담 이후 행동 기록`

두 번째 여정은 학생이 선택한 프로젝트를 실행하기 위한 연결입니다.

`AI 프로젝트 공동설계 → 프로젝트 후보 선택 → 실행에 맞는 교수 추천`

첫 교수 매칭의 질문은 “내 고민을 누구에게 무엇이라고 물어볼까?”입니다. 프로젝트 교수 추천의 질문은 “이 프로젝트를 성공적으로 실행하려면 어떤 전문성이 필요할까?”입니다. 같은 교수 추천처럼 보여도 성공 기준이 다르기 때문에 두 흐름을 명확히 분리했습니다.

[사진 4. `11-service-journey.png` — 서비스 전체 사용자 흐름]

## 같은 학과 교수부터 현실적인 첫 접점을 만들었습니다

교수 3인 피칭 화면에서도 사용자가 막혔습니다. 세 명의 교수와 여러 정보를 한꺼번에 보여주니 누구를 왜 먼저 선택해야 하는지 판단하기 어려웠습니다.

저희는 대학생이 본인 학과 교수에게 상대적으로 전공 맥락을 설명하고 접근하기 쉽다는 점에 주목했습니다. 그래서 첫 번째 후보는 같은 학과의 ‘가까운 시작점’으로 제안하고, 나머지 두 후보는 다른 학과의 ‘주제 연결형’과 ‘방법 연결형’으로 구성했습니다.

이 세 후보는 순위가 아닙니다. 같은 학과 교수는 가까운 첫 접점이고, 주제 연결형 교수는 관심 분야를 선명하게 만드는 선택지이며, 방법 연결형 교수는 필요한 역량과 접근법을 물어볼 선택지입니다.

카드에 있던 여러 버튼도 정리했습니다. 주 행동은 ‘이 교수님과 첫 대화 준비하기’ 하나만 남겼고, 이를 누르면 홈으로 돌아가지 않고 바로 만남 준비 화면으로 이동하도록 연결했습니다.

## 긴 프로젝트 입력 화면을 여섯 단계로 줄였습니다

프로젝트 설계 화면은 학교, 전공, 관심, 경험, 방법, 기간, 자료를 한 페이지에서 모두 입력하게 되어 있었습니다. 처음 들어온 학생은 입력을 시작하기 전에 긴 스크롤부터 마주했습니다.

이를 `방향 → 전공 → 관심 → 준비 → 실행 → 최종 확인`의 여섯 단계로 나눴습니다. 각 화면에서는 하나의 맥락만 확인하고, 이전·다음 버튼은 항상 같은 위치에 두었습니다. 답변은 브라우저에 자동으로 저장해 입력 방식을 바꾸더라도 앞서 작성한 내용이 사라지지 않게 했습니다.

PC에서는 단계 전체와 현재 입력을 함께 볼 수 있도록 하고, 모바일에서는 현재 질문과 다음 행동에 집중하도록 정보량을 줄였습니다. 모바일 교수 카드도 세 장을 세로로 길게 쌓는 대신 한 장씩 좌우로 넘겨 비교하게 바꿨습니다.

## AI 공동설계를 고정 설문이 아닌 맞춤 대화로 바꿨습니다

초기의 AI 공동설계는 이름과 달리 사용자마다 거의 같은 질문을 보여주고 있었습니다. 완전한 자유 대화로 만들면 사용자별 결과를 비교하기 어렵고, 모든 질문을 고정하면 개인화의 의미가 약해지는 문제가 있었습니다.

그래서 두 방식을 결합했습니다. 먼저 모든 사용자가 공통으로 답하는 세 질문을 통해 문제, 대상, 기대 변화를 정리합니다. 이후 OpenAI API가 앞선 답변의 빈칸과 조건을 살펴 맞춤 후속 질문 두 개를 만듭니다.

API 응답이 늦거나 실패해도 사용자가 처음부터 다시 입력하지 않도록 기존 답변을 보존하고, 검수된 기본 질문으로 흐름을 이어갑니다. AI가 프로젝트의 정답을 확정하는 것이 아니라 사용자가 비교할 수 있는 두 개의 프로젝트 후보와 확인해야 할 항목을 정리하도록 했습니다.

첫 화면에서 AI가 말하는 문장도 수정했습니다. 사용자가 아직 답하지 않았는데 “좋은 질문이에요”라고 말하던 어색한 문장을 없애고, 사용자의 전공과 앞선 입력을 바탕으로 어떻게 대화가 진행되는지 먼저 설명하도록 바꿨습니다.

## 교수 추천을 실제 첫 대화 준비까지 연결했습니다

교수를 선택한 다음에는 논문 한입, 첫 질문, 이메일 초안, 면담 이후 7일 행동으로 이어집니다. 교수의 공개 논문과 프로필을 읽고 무엇을 질문할지 준비하며, 이메일은 AI가 자동으로 보내지 않고 학생이 직접 검토하고 연락하도록 했습니다.

교수의 면담 가능 여부나 학생 모집 여부도 AI가 추측하지 않습니다. 공식 정보로 확인할 수 있는 내용, AI가 제안한 내용, 교수에게 직접 확인해야 하는 내용을 구분했습니다.

[사진 10. `before-after-2026-08-24/04-meeting-before-after.png` — 숨겨진 준비 도구를 만나기 전·대화 중·만난 후 진행표로 바꾼 전후 비교]

추천 결과가 한 번 보고 사라지지 않도록 ‘나의 성장과정’ 탭도 만들었습니다. 학생이 처음 입력한 관심과 진로 고민, 구체화한 프로젝트, 연결한 교수, 준비한 질문과 다음 행동을 시간의 흐름에 따라 확인할 수 있습니다.

여기에는 ‘나의 AI 교수님’도 추가했습니다. 실제 교수를 대신하는 기능이 아니라, 교수와 만나기 전후에 혼자 막히는 생각을 가볍게 정리하는 상시 사고 파트너입니다. 대화 전체가 자동으로 기록되는 것은 아니며, 사용자가 직접 선택한 요약만 성장 메모로 저장됩니다.

## 코덱스 X 클로드 바이브코딩 1~2강을 듣고 적용한 점

이번 개발에는 코덱스 X 클로드 바이브코딩 강의 1~2강에서 배운 기준도 직접 적용했습니다.

1강에서 가장 기억에 남은 내용은 아이디어가 나빠서 못 만드는 것이 아니라, 처음부터 너무 크게 잡아서 완성하지 못할 수 있다는 점이었습니다. 프로젝트를 ‘입력 → 반응 → 형태’의 한 문장으로 정의하고 오늘 완성할 수 있는 크기로 줄이는 아이디어 다이어트가 필요했습니다.

저희도 교수 추천, 프로젝트 설계, 만남 준비, 성장 기록을 한 화면에서 모두 설명하려던 방식을 버렸습니다. 각 화면의 핵심 행동을 하나씩 분리하고, 긴 입력 화면을 여섯 단계로 나눴습니다. 기능을 빼는 일이 손해가 아니라 사용자가 덜 헤매게 만드는 설계가 될 수 있다는 것을 실제로 체감했습니다.

2강에서는 AI가 만든 결과만 얻는 것보다 “이 행동은 왜 필요한지, 어떤 문제를 해결하는지, 이번 과정에서 무엇을 배울 수 있는지” 계속 질문하는 태도가 중요하다는 점을 배웠습니다.

이번 작업에서도 단순히 “화면을 예쁘게 바꿔줘”라고 요청하지 않았습니다. 사용자가 왜 다음 버튼을 찾지 못하는지, AI의 첫 문장이 왜 어색한지, 어떤 정보까지 AI가 말해도 되는지 계속 질문했습니다. 수정 전후 화면을 기록하고 PC·모바일에서 확인하며, 반복 점검은 테스트와 체크리스트로 남겼습니다.

아이디어는 있지만 어디서부터 만들어야 할지 막막하거나, AI가 만든 코드를 그대로 받는 데서 끝나지 않고 직접 질문하고 수정하며 작은 MVP를 완성해 보고 싶은 분께 추천하고 싶은 강의였습니다.

- Next.js 프로덕션 빌드 성공 및 45개 정적·동적 페이지 생성 확인
- 주요 페이지의 HTTP 200 응답 확인
- PC 1440×900과 모바일 390×844 화면에서 핵심 흐름 확인
- 브라우저 콘솔 오류와 경고 0건 확인

다만 이 결과를 실제 학생 사용성이 입증됐다고 표현하지 않으려고 합니다. 현재 확인한 것은 구현과 내부 시나리오입니다. 실제 대학생이 첫 매칭과 대화 준비를 끝까지 완료하는지는 별도의 사용자 검증이 필요합니다.

## 이번 주에 얻은 인사이트

처음에는 AI가 더 많은 답을 보여주면 좋은 서비스라고 생각했습니다. 멘토링과 반복 구현을 거치며 생각이 바뀌었습니다.

학생에게 필요한 것은 화려한 추천 결과가 아니라 자신의 고민을 말로 정리하고, 믿을 수 있는 근거를 확인하고, 실제 사람에게 첫 질문을 건넬 수 있는 작은 다음 행동이었습니다.

이번 주에는 기능을 많이 추가하지 않았습니다. 긴 화면을 나누고, 숨겨진 다음 행동을 꺼내고, AI의 말을 다시 쓰고, AI가 판단하지 않아야 할 경계를 분명히 했습니다. 이 과정에서 UX는 단순히 화면을 예쁘게 만드는 일이 아니라 사용자가 해야 할 판단을 줄이는 일이라는 점을 배웠습니다.

## 다음 주 계획과 역할 분담

다음 주에는 실제 대학생 3~5명을 대상으로 첫 매칭과 첫 대화 준비 흐름을 검증할 예정입니다. 첫 화면에서 시작 방법을 바로 이해하는지, 어느 단계에서 가장 많이 멈추는지, 교수 선택 후 만남 준비로 자연스럽게 이동하는지를 확인하겠습니다.

- 이연수: 사용자 테스트 시나리오와 최종 발표 스토리라인 정리, 전체 UX 보완
- 최현규: 코드 통합, 빌드·배포 및 핵심 사용자 흐름 회귀 점검
- 이진재: 교수 공식 정보와 출처 검수, 테스트 피드백 및 발표 근거 정리

테스트 결과를 바탕으로 카드에 남길 정보와 줄일 정보, 역할 명칭, 신뢰 안내 문구를 마지막으로 보완할 계획입니다. 최종 발표에서는 기능의 개수보다 ‘AI 추천 앱’이 멘토링을 통해 ‘실제 첫 대화와 다음 행동을 만드는 서비스’로 변화한 과정을 보여드리겠습니다.

## 마무리

‘너의 교수님은?’은 AI가 학생의 진로나 프로젝트 정답을 대신 결정하는 서비스가 아닙니다. 학생이 자신의 고민을 정리하고, 공식 근거를 확인하고, 교수와 첫 대화를 시작할 수 있도록 돕는 서비스입니다.

커널아카데미 UNIKER AI 크루 활동을 통해 처음의 가설을 화면으로 만들고, 멘토링과 QA를 반복하며 제품의 중심 질문을 바꿀 수 있었습니다. 앞으로는 실제 학생의 사용 경험을 통해 이 흐름이 정말 첫 대화까지 이어지는지 검증해 보겠습니다.

이번처럼 아이디어를 실제 서비스로 옮기는 과정을 직접 경험하고 싶다면, 코덱스 X 클로드 바이브코딩 강의에서 작은 MVP를 정의하고 AI와 함께 완성하는 흐름부터 시작해 보셔도 좋겠습니다.
